# Marketplace workflows (as implemented)
**Posting:** choose engagement type → details. Rules: numeric pay required; max ≥ min; pay basis must fit engagement (e.g. fixed project ⇒ fixed fee); fixed fee needs ≥20-char deliverables; local/hybrid needs an area; recurring needs hours/week + schedule; shifts need schedule; deadline ≤ start date; mandatory skills ⊂ requested skills. Status: draft → published, or → `pending_review` if the category `requires_approval` or setting `moderation.all_postings` is true. A failed publish keeps the user's entries as a draft and shows the error.
**Application statuses:** submitted → under_review → shortlisted → interview_requested → offer_received → accepted (worker) · declined (business, or worker on an offer) · withdrawn (worker). Terminal states can't change. Every change writes history + audit; notifications are written to `notifications`. Accepting locks the opportunity row; when accepted count ≥ `workers_needed` the opportunity becomes `filled`, and further acceptances fail.
**Eligibility to apply:** verified email, published & open opportunity, active business, deadline not passed. Applying is *not* blocked by match score; the score is a stored informational snapshot.

**Matching** (`src/server/matching/score.ts`)
- *Mandatory* (configurable set, default all on): required skills; availability for the requested weekly windows (coverage > 0 and not unavailable for the whole date range); travel radius for local work; worker's explicit hard-minimum hourly rate. Failing any ⇒ ineligible, never traded off.
- *Weighted* (default weights 30/25/12/8/10/6/4/5 for skills/availability/location/arrangement/compensation/experience/duration/preferences), only over criteria that can be assessed. Unknown data is excluded and reported as such.
- *Confidence:* raw score is scaled 60–100% by the share of weight assessable, so sparse data can't yield 100/100. `coverage` is returned and shown.
- *Tiers:* strong (≥ strong threshold, no gaps, coverage ≥ 50%), good, partial, not_recommended (< recommend threshold or ineligible).
- *Explanations* are built only from recorded reasons. Inputs exclude age, gender, parental status and any protected characteristic.
- Rules are versioned (`matching_rules`); admin changes publish a new immutable version.
- Availability is evaluated per weekday in minutes. It does **not** yet check conflicts with other bookings (no assignments exist) or time-zone conversion beyond a stored zone.

**Shortlist & invitations:** businesses shortlist or invite only *discoverable* workers (opted in, onboarded, verified email, active). Invites go only to the business's own published opportunities, are limited to 20/day/business, are blocked for existing applicants, and the invite flips to `accepted` when the worker applies. Workers may decline; never obliged.
**Messaging:** a thread exists only where a real relationship exists (application, invitation or assignment). One thread per business–worker pair. Non-participants get "not found". Businesses see workers as "First L." Emails, phone numbers and WhatsApp/Telegram links are rejected until an assignment (not cancelled) exists between the pair (off-platform safeguard — a heuristic, not a guarantee). 30 messages/minute/user; recipients can report messages (stored for review; there is no admin report-review screen yet).
**Assignments:** created automatically when a worker accepts an offer; agreed pay = worker's proposed hourly rate if given, else the posted minimum (snapshot, cents). Lifecycle: confirmed → in_progress (worker start) → submitted (note; hours required for hourly; optional link) → completed (business approves) or changes_requested (reason required) → resubmit. Either party may cancel before completion with a reason (the worker cannot cancel while work awaits review). Full history + audit. Hours are recorded on submissions but do **not** yet drive payment.
**Reviews:** only after completion, one per party, 1–5 overall plus optional quality/communication/reliability/professionalism. **Blind:** the other party's review is hidden until both have reviewed or 14 days after completion; only revealed reviews count toward a worker's public rating shown to businesses.
**Screening questions:** up to 5 per posting (5–300 chars, required or optional); every required one must be answered to apply; answers are stored per application and shown to the business. Questions are frozen once any application exists.
**Attachments:** up to 3 files × 10 MB on a message or a work submission. Types are allow-listed (pdf, png, jpg/jpeg, docx, xlsx, csv, txt) and each is checked against its real content; the client MIME type is ignored. Files are stored privately under random keys and served only through `/files/<id>` after an authorisation check (conversation participants / assignment parties; an admin only while the message has an open report, audited). Downloads are forced as attachments with `nosniff` and a sandbox CSP. **There is no malware scanning** (`scan_status` stays `unscanned`; the UI says so).
**Email notifications:** in-app notifications always; email per category (applications, messages, assignments, invitations, reviews) unless the user opted out, only to verified active accounts, never containing message text, message emails throttled to one per 15 minutes. Emails are queued in `email_outbox`; `npm run emails:send` delivers them when `EMAIL_DRIVER=smtp` (retries up to 5×; a row is `sent` only after the SMTP server accepts it). With the default `outbox` driver nothing is delivered.
**Reports & moderation:** recipients report messages; the reviewed party reports a review. Admins with `reports.review` see only the reported message plus up to 3 preceding messages; each view is audit-logged. Outcomes: message report actioned/dismissed (sender can be suspended from the same page); review report → hide (removed from display and ratings) or dismiss. Notes are mandatory.
**Not implemented:** work-sharing/coverage, services marketplace, recurring management, handovers, disputes, hour-based payments.
