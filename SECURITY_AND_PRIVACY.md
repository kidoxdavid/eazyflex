# Security and privacy (implemented vs not)
**Implemented:** argon2id passwords (≥10 chars, letters+number); hashed single-use verification/reset tokens with expiry; verification is a POST (prevents link-scanner consumption); generic login/reset responses; constant-ish time for unknown emails; DB-backed rate limits (login per email/IP, reset per email); sessions hashed at rest, httpOnly+SameSite cookie, revoked on reset/suspension; server-side authorisation in services + route guards; Zod validation everywhere; parameterised queries (Drizzle) — one raw-SQL helper is parameterised; React output escaping, JSON-LD escapes `<`; open-redirect guard on `next`; security headers (nosniff, frame deny, referrer, permissions-policy); append-only audit log; messaging limited to participants with an existing relationship, contact-detail guard and rate limit, workers shown to businesses as "First L."; assignment/message/review access returns not-found to outsiders and role cannot be spoofed; blind reviews (anti-retaliation); worker privacy (businesses see "First L.", skills, area, availability — never email/phone/address; opt-in `public_profile`; approximate areas only); no SIN/bank/card/ID-document collection; postal code limited to the first 3 characters; consent records with policy versions; "unverified" never shown as verified.
**Hardening round (implemented):**
- *Content-Security-Policy:* per-request nonce via `src/proxy.ts`: `script-src 'self' 'nonce-…' 'strict-dynamic'` (no inline/eval scripts in production), `object-src 'none'`, `frame-ancestors 'none'`, `base-uri`/`form-action 'self'`, no third-party origins (fonts are bundled). One deliberate relaxation: `style-src-attr 'unsafe-inline'`, because inline style *attributes* (the coverage chart) can't carry a nonce; style *elements* still need self/nonce. Verified in a real browser: no CSP violations on the key pages. Also HSTS (production), COOP/CORP `same-origin`, `X-Frame-Options`, `nosniff`, tightened Permissions-Policy.
- *Sessions:* the cookie is `__Host-`-prefixed in production (Secure, HttpOnly, SameSite=Lax, path `/`, no Domain); administrator sessions last 8 h (others 30 days); sessions are revoked on password reset, suspension and MFA reset.
- *Admin two-factor authentication:* TOTP (RFC 6238, checked against the RFC test vectors) with 8 one-time recovery codes (stored as SHA-256 hashes). The seed is AES-256-GCM encrypted at rest with `APP_SECRET`. Each 30-second step is usable once (atomic replay protection); failures are rate-limited (8 per 10 min) and audited. Enforced on **every** admin page and server action (`requireUser`), not just at login: `MFA_ENFORCEMENT=required` (the production default) forces enrolment; once enrolled, an admin is always challenged. A super administrator can reset a colleague's 2FA (revokes their sessions; audited). The demo admins share a PUBLIC demo seed (see README) — it exists only on seeded demo accounts.
- *Throttling:* sign-in and 2FA throttles count **failed** attempts only (a shared office address can't be locked out by successful sign-ins); registration is limited per IP.
- *Data rights (PIPEDA/PIPA):* **Export** — `POST /account/export` returns the person's own data as JSON (profile, applications, assignments, their messages, reviews they wrote, preferences, activity); never password hashes, tokens, 2FA material or other people's personal data (counterparties appear as a business name or "First L."); 3 per day. **Deletion** — anonymise in place after password + typed confirmation: name/email/phone erased; profile, skills, availability, saved items, notifications, sessions, tokens, 2FA and uploaded files (blobs removed) deleted; message text, review comments and application text scrubbed; reviews *about* them removed; open applications withdrawn; the email address becomes reusable. Retained so other people's records stay coherent: assignment records (pay, dates, status — no longer identifying), the other party's side of conversations, ratings they gave (comments removed), consent records, and append-only audit entries (opaque user id only). Blocked while the person has active assignments or confirmed shift slices; a business owner must first remove team members and finish active work. Admin accounts are removed by a super administrator, not self-service.
- *Not covered by the data-rights tooling:* backups (deleted data persists until backups roll off — a retention window must be defined), data held by email/hosting providers, and an operator workflow for erasure requests that arrive by email.

**Operations hardening (implemented):** structured JSON logs with scrubbing; Sentry-compatible error reporting with de-duplication and PII scrubbing; request ids; liveness/readiness endpoints; **malware scanning of uploads through clamd (fails closed when required — default in production)** with infected files blocked and audited; **S3-compatible private storage driver** with server-side encryption (tested against a fake S3 endpoint: real-service compatibility must be confirmed in staging); encrypted backups with CI-run restore drill and a deletion ledger so restores don't resurrect erased people; scheduled retention purge; static authorisation-coverage tests. See RUNBOOK.md, THREAT_MODEL.md, LAUNCH_CHECKLIST.md.

**Team access:** role checks in the service layer on every business write (members cannot post, hire, edit the profile, manage coverage/renewals or review); invitation tokens hashed, single-use, expiring, bound to the invited email; DB-enforced single owner and single business per person; removal takes effect immediately (no session reload needed). **Uploads (implemented):** extension allow-list + magic-byte check, size/count limits, random private keys, authorised same-origin download route (no public/signed URLs), forced attachment + nosniff + sandbox CSP, admin access only to reported content and audited. **Not implemented / required before launch:** a clamd instance to run and keep updated (the scanner client is built and tested; the AV engine itself is operated by you), confirmation of the S3 driver against your real provider, encryption-at-rest configuration (infra), secrets manager, backup/DR runbook and a backup-retention policy for deleted data, email-sending SPF/DKIM and CASL consent flows, password-breach (HIBP) checks, WebAuthn/passkeys (admin 2FA is TOTP only), step-up re-authentication for the most sensitive admin actions, a CSP violation-reporting endpoint, penetration test, a non-owner DB role (so audit triggers can't be dropped), distributed rate limiting at the edge, legal review (Alberta employment standards, agency licensing, classification, OHS, WCB, insurance, tax, background checks, vulnerable-sector screening).
